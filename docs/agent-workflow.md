# Работа нескольких агентов

Рабочая единица — небольшая задача с проверяемым результатом. Координатор ведёт статус,
зависимости и исполнителя в GitHub Issues, спецификации и решения — в Git.
Порядок закрытия задач и полномочия описаны в [organization.md](organization.md).
Правила опираются на [AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md),
[skills](https://learn.chatgpt.com/docs/build-skills) и
[subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents).

## Роли

| Роль | Ответственность |
|---|---|
| Координатор (основной агент) | Задачи, разделение файлов, интеграция, простой отчёт владельцу |
| Android engineer | BLE, фоновая запись, хранение, UI |
| Measurement engineer | Физика, timing, алгоритм, replay и исследования |
| Reviewer | Независимая проверка корректности и обоснованности заявлений, read-only |
| Tester | Воспроизводимые проверки конкретного SHA; без изменения продуктового кода |

Конфигурации `.codex/agents/*.toml` описывают специализированные роли, без привязки
к конкретной модели. В среде без поддержки custom roles передавайте эти инструкции
обычным агентам вручную через координатора. Конфиги синтаксически проверены; их
фактическую загрузку конкретным клиентом Codex проверять при начале новой сессии.

## Цикл задачи

1. Координатор читает или создаёт Issue по `docs/tasks/TEMPLATE.md`, задаёт scope, base SHA, владельца,
   допустимые файлы, зависимости, критерии приёмки и бюджет проверок.
2. Один пишущий агент получает отдельный worktree. Из корня, после первого commit:

   ```bash
   git worktree add .worktrees/JG-001 -b task/JG-001 main
   ```

   Базовый SHA записывается в задачу; не подтягивать движущийся main в середине
   эксперимента без причины. Вложенные worktrees игнорируются Git. Удалять только
   после интеграции и проверки чистоты, без force. Команды выполняет координатор.
3. Автор реализует и делает профильную проверку. Общие контракты/build-файлы
   принадлежат одному агенту, остальные ждут готовый commit.
4. Независимые reviewer/tester получают один кандидатный commit и критерии.
   Ревью можно делать параллельно тестам; разные телефоны/наборы данных — только
   с явно назначенным владельцем ресурсов. Общий датчик обслуживает один агент.
5. Исправления — автору; повторять только затронутые проверки. Координатор публикует
   отчёты в PR, интегрирует через PR с обязательным CI, проверяет итоговый SHA.
   Issue закрывается только по критериям organization.md; merge не заменяет hardware-приёмку.
6. Владелец получает результат и при необходимости короткую физическую инструкцию.

Не запускать оркестратор ради самого оркестратора. Не нужны отдельный сервер агентов,
платная платформа задач, рекурсивные команды или автоматические бесконечные циклы исправлений.
Инструкции помогают дисциплине, но не заменяют проверки, sandbox и защиту main.

## Передача контекста

В handoff достаточно: цель, состояние/commit, изменённые файлы, решения с ссылками,
известные ошибки, что реально проверено, что пропущено, следующий конкретный шаг.
Параллельные авторы не редактируют общий файл задач: отчёты передают координатору.
Не сохранять в отчётах секреты и личные идентификаторы участников.
