# План разработки

Текущий этап: 0. Последовательность учитывает, что точность важнее количества экранов.

| Этап | Результат | Условие перехода |
|---|---|---|
| 0. Основа | Git, правила агентов, навыки, bootstrap CI, план экспериментов | Локальные проверки основы; GitHub CI проверяется после подключения remote |
| 1. JG-001 | Собираемый Android-каркас и проверка toolchain | Debug APK, unit/lint/build CI, запуск на S26+ или явный статус ожидания устройства |
| 2. Регистратор | BLE-подключение, start/stop, screen-off, raw export, gaps | Разобран реальный capture, проверены протокол/частота/30 минут записи |
| 3. Пилот | Синхронные записи с эталоном, разметка, фиксированный split | Согласована измеряемая величина и пригодность эталона; известны ограничения |
| 4. Алгоритм | Replay, сравнение методов, quality rejection | Пройдены заранее фиксированные критерии docs/measurement.md на holdout |
| 5. MVP | Прыжки/баскетбол/волейбол, история и итоговая статистика | 90-минутные записи; приёмка каждой заявленной активности; понятный отчёт погрешности |
| 6. Спортивные категории | Исследование блок/атака/подача | Достаточная разметка и доказанная различимость; отдельное решение о реализации |

Этапы 1–2 не ждут спортивного датасета. После стабильного формата записи UI и анализ
могут развиваться параллельно в отдельных worktrees. Алгоритм не строится на выдуманных
пакетах, UI не выдаёт экспериментальную оценку за проверенную.

В MVP: один датчик, одна активность на сессию, старт/стоп, длительность, количество,
список высот, максимум/среднее валидных прыжков, покрытие записи, история, экспорт/удаление.
Автопауза, live-рекомендации, аккаунт, облако, команды и классификация — вне первого MVP.

От владельца ближайшие входы: версия Android/One UI, фото/сведения о маркировке и прошивке
при первом подключении, способ крепления, возможность снять замедленное видео и доступ
к эталону высоты. Эти вопросы не блокируют инфраструктуру и Android-каркас.
