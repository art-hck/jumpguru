# WT9011DCL: профиль BLE для реализации

Версия документа: 1, 2026-09-20. Статус: документальный кандидат, hardware acceptance
не пройден. [Источники S3–S7](sources.md); [план проверки](validation.md).
Это требования к будущему адаптеру, не реализованный декодер/контракт хранения.

## Подключение

S7 Python `openDevice` и Java `DeviceModel` используют:

| Назначение | UUID |
|---|---|
| Service | `0000ffe5-0000-1000-8000-00805f9a34fb` |
| Notify (в SDK назван READ_UUID) | `0000ffe4-0000-1000-8000-00805f9a34fb` |
| Write | `0000ffe9-0000-1000-8000-00805f9a34fb` |

Сначала discovery реального GATT и проверка properties/дескрипторов, затем подписка.
Эти UUID — подтверждённые значения примера, не результат сканирования нашего датчика.
Имя устройства — подсказка для выбора, не основание декодирования. Несовпадение профиля
показывать как unsupported/unknown, не переключаться на UART-декодер.

Подписка, чтение и запись GATT сериализуются с таймаутами и ограниченными повторами;
успешная постановка write в Android не означает применения настройки. Тип записи
выбирать по подтверждённым properties и протоколу. Read-register здесь тоже команда
через write characteristic, а не Android GATT read.

Не переносить старые разрешения Location/Storage из S3 в современный Android.
При реализации сверить target/runtime SDK с официальными
[BLE permissions](https://developer.android.com/develop/connectivity/bluetooth/bt-permissions)
и [background BLE](https://developer.android.com/develop/connectivity/bluetooth/ble/background).
Запись — foreground service `connectedDevice`, запущенный пользователем; lifecycle
экрана и частота обновления UI не должны управлять частотой сохранения данных.

## Кадр `55 61`: сначала установить режим

S4 с.12–14 и S7 описывают 20 байт: заголовок и девять signed int16 little-endian.
**S5 с.4–5/14 добавляет регистр 0x96:** значение 0 — IMU, 1 — перемещение/скорость/углы.
Оба режима имеют `55 61`. Поэтому одного заголовка недостаточно.

Для измерений JumpGuru профиль допускает только подтверждённый IMU-режим.
Если регистр отсутствует у старой прошивки, подтвердить старый профиль комбинацией
версии, документации этой ревизии и статических/осевых capture. Отсутствие ответа
не означает «режим 0». До подтверждения сохранять raw, не выдавать SI/высоту.
После reconnect/возможного изменения конфигурации подтверждение должно быть восстановлено.
Состояния профиля: unknown → identified → IMU mode verified → capture validated.
Признаки противоречия возвращают профиль в unknown и начинают новый сегмент.

| Смещение (с нуля) | IMU-режим | Преобразование |
|---|---|---|
| 0–1 | `55 61` | Маркер, не checksum |
| 2–7 | Ax, Ay, Az | `int16 / 32768 × 16` g |
| 8–13 | Wx, Wy, Wz | `int16 / 32768 × 2000` °/с |
| 14–19 | Roll, Pitch, Yaw | `int16 / 32768 × 180` ° |

Signed conversion: `u = low | (high << 8)` с unsigned байтами;
`n = u >= 32768 ? u - 65536 : u`. Не округлять перед сохранением/анализом.
Проектный коэффициент перевода g в SI — `g0 = 9.80665 m/s²` (стандартная единица g,
не измерение местной гравитации); °/с → rad/s умножением на π/180; углы → rad.
Физическое g алгоритма и коэффициент единицы должны иметь явные версии/назначения.

S4/S5 описывают ZYX, но текст перевода осей неоднозначен. До реальной проверки нельзя
считать установленными `R_body_to_world`, направление quaternion и порядок компонентов
в математической библиотеке. Проверить повороты, знаки, горизонталь и окрестность ±90°.

В схеме `55 61` нет места для timestamp, sequence или прикладного checksum: все 20 байт
заняты. Противоречивую формулу `55 59` из раздела quaternion не применять к BLE.
Это не утверждение об отсутствии контроля ошибок на нижних уровнях Bluetooth.

## Ответ `55 71` и дополнительные каналы

S4 с.15–18, S5 с.7–10: 20 байт = `55 71`, двухбайтовый LE start register,
затем восемь двухбайтовых регистров. Проверять весь адрес, а не только byte 2 как в S7.
Смысл и signedness зависят от регистра; не преобразовывать все регистры в signed физику.

| Start register | Read-команда | Что известно / ограничение |
|---|---|---|
| 0x2E | `FF AA 27 2E 00` | Содержит 0x2E и 0x2F: сохранить raw версии; формулы S4/S5 различаются |
| 0x3A | `FF AA 27 3A 00` | Hx/Hy/Hz; единицы/масштаб конфликтуют, пока только raw |
| 0x51 | `FF AA 27 51 00` | Q0–Q3, signed/32768; конвенцию и свежесть проверить |
| 0x40 | `FF AA 27 40 00` | Температура, signed/100 °C по S4/S5; для SI добавить 273.15 K |
| 0x64 | `FF AA 27 64 00` | Java S7 трактует raw/100 как V; таблицы процента заряда расходятся |
| 0x03 | `FF AA 27 03 00` | Проверка RATE; поддержка readback на устройстве ещё не установлена |
| 0x96 | `FF AA 27 96 00` | AGPVSEL из S5; на старом устройстве может отсутствовать |

Восьмёрка регистров ответа не доказывает атомарное измерение всех значений.
Неизвестные регистры сохраняются без придуманных единиц. S4/S5 перечисляют время
0x30–0x33, но не определяют подтверждённую для нас связь с каждым кадром IMU.
Опрос часов отдельно не превращается в sample timestamp; device time/sequence остаются
nullable. Поддержку, ход часов, сброс и связь с выборками исследовать отдельно.

Python S7 отдельно опрашивает магнитометр/кватернион; Java — магнитометр/батарею.
Общий словарь SDK содержит значения разного возраста. Для JumpGuru каждое обновление
имеет собственные receive time, источник и age; нельзя записывать старый quaternion
как новый при каждом IMU callback. Сравнить нагрузку с дополнительным polling и без него.

## Изменение настроек: только проверенный профиль

Согласованная между S4/S5/S7 часть RATE: `FF AA 03 RATE 00`,
10 Гц → 0x06, 50 → 0x08, 100 → 0x09, 200 → 0x0B.
Сохранение: `FF AA 00 00 00`; `FF AA 00 01 00` — factory reset, не обычный save.
Это справочник байтов, не разрешение отправлять команды в рамках исследования.

Unlock, BANDWIDTH и версии имеют [явные расхождения](sources.md). Не делать автоматические
попытки разных unlock/таблиц. До аппаратного подтверждения нет универсальной безопасной
последовательности записи. Сначала baseline/readback и сверка ревизии; затем одна
контролируемая смена настройки по применимому документу с сохранением before/after.
Журналировать TX bytes, receive response, таймауты, ожидаемый/прочитанный результат;
не путать readback с доказательством фактической частоты/полосы.
Проверять сохранение после power cycle отдельно, не доверять только полю в vendor UI.
Не сбрасывать factory settings и не менять calibration/output mode при обычном reconnect.

## Raw, время и ошибки

[Архитектура](../architecture.md) остаётся источником будущего контракта записи.
Дополнения для проектирования схемы: версия профиля, raw настройки/версия устройства,
статус подтверждения режима и история команд; это требования, не новая схема файла.

- Сохранить bytes каждого notification, characteristic, монотонное время приёма,
  connection epoch и исходные границы до декодирования. Неполные/неизвестные данные
  сохранять тоже. Raw означает байты BLE, а не неотфильтрованные отсчёты MEMS.
- При сборке логического кадра из нескольких notification сохранять связь со всеми
  исходными пакетами; его receive time не становится временем измерения. Не склеивать
  хвосты через reconnect. Неполный хвост/ресинхронизация — диагностическое событие.
- Границы notification не подменяют контракт декодера. Проверить split/coalesced кадры,
  шум перед header, неизвестный flag, обрыв в конце и попадание `55 61` внутрь payload.
  Без checksum правдоподобный header не гарантирует правильное выравнивание.
- Разделять число callbacks, байтов, полных IMU-кадров и обновлений доп. каналов.
  Средняя скорость доставки и квантили интервалов — наблюдаемые метрики; частота
  физических измерений и точное число радиопотерь могут оставаться неизвестными.
- Явные disconnect, overflow, storage failure разбивают запись. Порог наблюдаемой
  паузы версионируется по профилю; UI не должен выдавать оценку покрытия за точную
  долю успешно принятых физических samples.

Расчёт ёмкости для планирования: при одном 20-байтовом IMU-кадре на отсчёт 200 Гц
это 4000 B/s и 21.6 MB за 90 минут **только payload**. Метаданные, дополнительные
ответы, журнал и индексы увеличивают объём. Это арифметическая оценка, не benchmark.

## Что не копировать из демонстрационного SDK

Наблюдения статического чтения S7, не отчёт запуска:

- Python округляет значения, блокирует asyncio через `time.sleep`, вызывает async
  `sendData` в `unlock`/`save` без await. Это не образец надёжной очереди команд.
- Java создаёт буфер заново на каждый callback: неполный кадр не переживёт следующий
  callback. Отправка/сохранение по задержке и boolean GATT не подтверждают настройку.
- Обе реализации обновляют словарь каналов, а не журнал сырых пакетов; диагностическая
  печать/вывод на экран не заменяют регистратор.
- Ни одна из прочитанных реализаций `55 61` не проверяет новый режим 0x96.

Решение: небольшой собственный тестируемый адаптер по проверенному профилю;
заимствование исходников/AAR — только после отдельной проверки лицензии и качества.
