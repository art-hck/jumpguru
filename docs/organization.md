# Организация работы

Согласовано владельцем 2026-09-19. Правила распространяются на всех агентов проекта.

## Где находится актуальная информация

- [GitHub Issues](https://github.com/art-hck/jumpguru/issues) — статусы, исполнитель,
  зависимости, блокеры и итог задачи. Роль не равна назначенному исполнителю: при старте
  координатор записывает идентификатор агента, base SHA, ветку/worktree и границы файлов.
- Git — спецификации, критерии продукта, архитектурные решения, инструкции и код.
  В Issue давать ссылки на документы; не поддерживать вручную две независимые копии требований.
  При расхождении остановить зависимое действие и согласовать/устранить расхождение;
  старая формулировка Issue не отменяет новое решение владельца.
- PR — diff, candidate SHA, результаты CI и независимых reviewer/tester.
  Issue содержит ссылку на PR и итоговый merge SHA.
- Если GitHub недоступен, подготовить локальный handoff с пометкой «не синхронизирован»;
  после восстановления сначала перечитать Issue. Не объявлять удалённый статус обновлённым.

## Статусы

У открытой рабочей задачи ровно одна метка `status:*`.

| Метка | Смысл |
|---|---|
| status:planned | Работа ещё не началась; зависимости указаны в Issue |
| status:in-progress | Назначен агент, работа началась |
| status:review | Результат готов к проверке; перечислены незавершённые проверки |
| status:done | Критерии выполнены, итог записан, Issue закрыто как completed |

`blocked` — дополнительная метка к текущему статусу. Указать причину, кто снимает блокер
и следующий шаг. Для физической проверки дополнительно `needs:hardware`: приложить
версию APK и короткую инструкцию владельцу. Ожидание не является успешной проверкой.
Выполнение зависимости само по себе не запускает следующую задачу без назначения.
При отмене закрыть как not planned с причиной и убрать `status:*`; отмена не равна done.
При переоткрытии убрать done и выбрать фактический рабочий статус.

## Когда задача выполнена

1. Выполнены все её актуальные критерии. Изменение scope явно зафиксировано до закрытия.
2. Результат привязан к commit; для кода он интегрирован через PR, для исследования
   доступны разрешённые артефакты и выводы без публикации частных записей.
3. Выполнены проверки по изменению: команды, exits, среда и ограничения указаны в PR.
   Код написан, APK собран, аппаратный сценарий пройден — отдельные факты.
4. Для существенных изменений выполнено независимое ревью; для изменений поведения
   также проверка tester. Оба проверяют одинаковый candidate SHA. Новые исправления
   требуют проверки затронутого diff, а не автоматического полного повторения всего набора.
5. Обязательные аппаратные проверки не заменены эмулятором/моками. Если они ещё впереди,
   задача остаётся открытой с блокером. Допустимое разделение software/hardware оформляется
   явно с отдельной связанной задачей, а не незаметным удалением критерия.
6. Пользователь получает короткий итог: что доступно, что проверено, ограничения и
   следующий шаг. Он не обязан читать код, запускать тесты или редактировать документы.

Пропущенная проверка допускает закрытие только если она не входит в критерии задачи
или владелец явно согласовал исключение. Исключение никогда не считается доказательством
точности/готовности. Не использовать `Closes #...` до выполнения всех критериев: merge
может быть готов раньше проверки телефона. Тогда использовать `Refs #...`.

## Самостоятельность

В пределах порученной задачи агенты самостоятельно исследуют код/первичные источники,
создают worktree, пишут код и тесты, собирают debug APK, проводят ревью, делают push/PR,
обновляют Issue и сливают готовый PR после необходимых проверок. Автором записей GitHub
может быть аккаунт владельца; в отчёте указывается фактическая роль/агент.
Публикация диагностических логов предварительно требует очистки от приватных данных.

До отдельного согласования нельзя подключать ботов/сервисы/интеграции, включать новые
фоновые автоматизации, оформлять расходы, публиковать release/приложение в магазине,
загружать личные записи и видео, менять доступы или ослаблять защиту ветки.
Разрешение на одну интеграцию не означает разрешение на следующие. Существующий CI
можно развивать в рамках задачи сборки, без новых внешних сервисов и расходов.
Установленные навыки не расширяют эти полномочия. Запрос остановиться действует сразу.

## Защита main

Ожидаемая конфигурация хранится в [github-main-protection.json](github-main-protection.json).
Сам файл не включает защиту: её применяет координатор через API после поручения,
затем читает настройки обратно. Эта первоначальная настройка согласована владельцем.

- Обязателен PR, прямые push в main не используются.
- Требуется успешный `repository-checks` от GitHub Actions и актуальная относительно main ветка.
- Запрещены force-push и удаление main; правила действуют для администратора.
- Все review conversations должны быть разрешены до merge.
- GitHub approvals count = 0: агенты сейчас используют один аккаунт и не могут одобрять
  собственный PR. Независимый агент-review обязателен по процессу, его отчёт с SHA
  координатор публикует в PR. GitHub технически не проверяет независимость этого отчёта.
- Координатор не применяет `--admin` и не снимает protection для прохождения merge.

В JG-001 после первого успешного запуска предложить владельцу конкретные Android checks
для добавления в required checks; применить после отдельного согласования.
`repository-checks` проверяет только инфраструктуру. Не назначать несуществующие
имена checks, иначе merge заблокируется. Если main сдвинулась, обновить PR и повторить
затронутые проверки на новом SHA; strict protection — явная причина такого обновления.
Владелец с admin-доступом технически может изменить protection, поэтому это не защита
от владельца аккаунта и не полная изоляция агентов.
